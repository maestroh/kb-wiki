Agent Core — Design

A lightweight, embeddable Node package: an agent that uses kb-wiki as memory. Hand it an LLM client, a skills directory, and a kb-wiki path, then call chat(). It runs a multi-step reasoning loop, calls skills, recalls and persists knowledge — generic enough to back a chatbot or a larger agent system. Lightweight is the governing principle.

§ Why we're building it

The approved memory redesign already anticipates a headless agent backend (its Part G) that consumes the deterministic Layer 1 scripts. That backend exists today only as a rough prototype (willikins): a full Express app with a plan-execute pipeline. We want the clean, minimal version, extracted into a reusable package.

Not an app

A module a host imports — no server, no DB, no queue.

Not plan-execute

A simpler, more flexible loop suited to long-running, dynamic tasks.

Memory encapsulated

kb-wiki is fully hidden — the host never learns its internals.

This spec is the agent core only.It treats the memory contract as a fixed dependency and adds exactly one small extension to it (see the kb-wiki extension section).

§ Reuse vs. add

Almost everything about memory is already decided in the approved spec. We cite it rather than redesign it.

REUSED AS-IS — do not redesign
  • Layer 1 scripts: resolve, ingest, retrieve, compile-plan, compile-commit, core, sync
  • Registry-based project resolution; one repo / many projects; no manual naming
  • Read-merge wiki ∪ pending-raw (never stale)
  • Caller-side synthesis — no LLM inside the scripts
  • Always-loaded core/ memory tier
  • The on-disk contract & invariants, incl. the existing Raw Sources (archived) heading
ADDED BY THIS SPEC
  • The agent runtime itself — the two loops, guards, API, capture pipeline (Part G, made concrete)
  • One contract extension: an archivedPending drain path in compile
  • A headless resolution policy for the ambiguous/none cases the memory spec left to the backend

§ Locked decisions

Settled through brainstorming. Each shaped a fork; the lightest viable option won throughout.

1

Inner loop = ReAct

Iterative tool-calling, not plan-execute. Lightest build; best fit for dynamic, long-running tasks.

2

Deterministic guards

Wandering is controlled by in-loop limits (no LLM), not by a supervisor.

3

Outer loop = memory only

Persistence + compaction. It does not supervise the inner loop.

4

Recall is a tool

On-demand recall(query). Core facts always injected; project knowledge fetched only when asked.

5

Capture is automatic

Deterministic structural pre-clean of each exchange → ingest. Never the model's discretion; never the whole transcript.

6

Filter at compile

Meaning-filtering happens at compile, not capture. raw is generous staging; the wiki stays clean.

7

Compile is internal

Threshold-triggered off on-disk pending count, run best-effort in the background. The host never operates it.

8

Stateless

No conversation state between calls. The host owns history; kb-wiki on disk is the only durable state.

9

Auto project resolution

Registry-based; host never names a project. Headless ambiguity resolved by the in-loop reasoner.

10

OpenAI-compatible LLM

The openai SDK with a configurable baseURL. A thin LLMClient keeps it swappable.

11

Skills from willikins

Discovery → load → execute (subprocess), ported wholesale.

+

One kb-wiki change

An archivedPending drain so every reviewed source leaves pending.

§ Architecture overview

Two loops over a fixed memory dependency. The inner loop reasons and acts; the outer loop persists. All durable state lives in the git-backed kb-wiki repo.

§ Inner loop & guards new

A standard tool-calling loop. Each turn: assemble context, call the LLM with the tool set, execute any tool calls, append results, repeat. A turn with no tool call = done. Anti-wander is entirely deterministic — no supervisor, no extra LLM calls.

GuardMechanism
Step / token budgetHard cap (default 15 steps). At the cap, inject "out of budget — give your best final answer" and force a text-only turn. Nothing runs unbounded.
Goal re-anchoringThe original objective is pinned at the top of the system prompt every turn, so it can't drift as history grows.
Explicit terminationNative: a turn with no tool call ends the loop. Optional finish(summary) tool makes completion deliberate.
Repeat detectionHash each tool call (name + args). On a duplicate, inject "you already ran this; result was X — do something different or finish."
Error backoffAfter K failures of the same tool, stop retrying it and tell the model to route around it.

§ Memory pipeline reuses contract

Three jobs, deliberately separated: capture is reliable but dumb (deterministic, no LLM); compile is the smart filter (the one LLM step); recall reads the clean wiki, merged with still-pending raw so it's never stale.

Capture — the deterministic pre-clean

After the response is produced, the outer loop captures this exchange with a pure structural transform — no LLM, no semantic judgment. It drops only categorically-plumbing content. Rule: keep human-authored text + the agent's final prose; drop everything that is plumbing.

Transcript elementAction
system (scaffolding, goal re-anchoring)drop
user text (minus injected recall / reminder blocks)keep
assistant final prosekeep
assistant internal reasoningdrop
assistant tool_call (name + args)drop (optional 1-line trace)
tool_result dumps (file / command output, retrieve JSON)drop — the volume sink
retries / errors / duplicatesdrop

Pleasantries are not stripped here (that's semantic) — compile handles those. Division of labour: deterministic pre-clean removes structural noise (the bulk, by volume); compile removes semantic noise.

Project resolution — the headless policy new

resolve.ts runs on the cleaned exchange's signals (deterministic). The host never names a project.

Strong match

Ingest to that project. Zero cost, fully deterministic.

Ambiguous / none

The in-loop reasoner adjudicates — picks the best candidate or proposes a new project from content. This rides on reasoning the turn already did, so it's not an extra hot-path LLM call; deterministic ingest.ts then writes to the chosen project.

Compile — internal & self-managed

The disk is the state.The memory subsystem decides when to compile by reading pending-count from disk — compatible with statelessness. Over threshold → compile runs best-effort in the background after the response returns. Safe to defer/interrupt because compile-commit is idempotent and pending stays pending until consumed. The host never sees any of this.

§ Conversation & state

There isn't one "conversation" — there are three layers. We own two of them; the host owns the middle one. This is what "stateless" actually buys.

Stateless

No conversation state between calls. The host passes history in and appends the returned messages.

Granularity

One exchange (user msg → response) may span many internal turns. Capture keeps only the substance.

Compaction

Only matters if a single long chat() overflows the window. Persistent-log compaction is the host's concern.

§ Public API new

Stateless, generator-first. The generator is the core; run() is a thin collector. Everything memory is internal — the lone exception is sync() (deliberate, network + credentials, host-paced).

// 1. Construction — inject the three dependencies; sane defaults for the rest
const agent = createAgent({
  llm,                                    // LLMClient; default = OpenAI-compatible
  skills: { paths: ['./skills'] },        // willikins-style SKILL.md dirs
  memory: { kbPath: process.env.KNOWLEDGE_BASE, gitToken },
  systemPrompt,                           // persona / standing instructions
  guards:  { maxSteps: 15, maxTokens },   // deterministic anti-wander limits
  compile: { threshold: 10, model },      // internal trigger + optional cheaper model
});

// 2. Core — streaming async generator (stateless: history in, events out)
for await (const ev of agent.chat({ history, message })) {
  // ev: { type:'token', text }
  //   | { type:'tool_call',   name, args }   // a skill or recall
  //   | { type:'tool_result', name, ok }
  //   | { type:'done', response, messages }  // final text + messages to append
}

// 3. Convenience — non-streaming (drains the generator)
const { response, messages } = await agent.run({ history, message });

// 4. The one deliberate, host-triggered memory op
await agent.sync();
  • history is host-owned and read-only to the agent.
  • Returned messages = user message + final assistant message only — not the internal tool plumbing.
  • recall / ingest / compile are not public — recall is an internal tool; the rest are private.

LLM client

A thin LLMClient is the seam; the shipped default is OpenAI-compatible, lifted from willikins' llm.component.ts. OpenAI message shape is the internal format (no translation layer); tools are passed as OpenAI function defs; baseURL points at OpenAI, DeepInfra, Together, a local server, etc. The same client powers compile synthesis, with an optional cheaper compile.model override.

§ kb-wiki contract extension — archivedPending new

The only change to kb-wiki. Auto-capture produces more low-value pending than human ingest does. A cleaned-but-contentless exchange yields no article, so under today's contract it would never be in consumedPending, never leave pending, and be re-read on every compile (silting). Fix: a second drain so every reviewed source leaves pending.

FileChange
index-sections.tsAdd moveToArchived(body, paths, date) — a mirror of moveToCompiled targeting the existing ## Raw Sources (archived) heading. Raw file stays in place (immutable); only the index entry moves, which suffices since compile-plan reads only the pending section.
compile-commit.tsAdd optional archivedPending?: string[] to CommitInput; after moveToCompiled, call moveToArchived for it.
compile promptRule: "account for every pending source — each goes in consumedPending (became an article) or archivedPending (reviewed, nothing durable). Pending must be empty after a full compile."
Rejected fallback.Stuffing noise paths into consumedPending drains pending with zero code change, but mislabels them "compiled" — misleading kb-lint and human readers. Not worth it.

§ End-to-end trace

One call, start to finish.

  1. host: chat(history, "set up CI for payments; we deploy via Fly")
  2. Inject core facts + re-anchor goal; build working context from history.
  3. ReAct: recall("payments deploy") → [wiki ∪ pending] → run skill(s) → answer.
  4. Pre-clean this exchange (drop tool dumps / plumbing) → resolve project → ingest (pending).
  5. pending-count(disk) > threshold? → background compile (plan → synthesize → commit).
  6. Return { response, messages: [userMsg, assistantMsg] } — host appends.

§ Scope

IN SCOPE
  • The package — the two loops, guards, API, capture pipeline
  • The archivedPending contract extension
  • Porting willikins' skills + LLM layer
  • The headless resolution policy
  • Tests
OUT OF SCOPE / DEFERRED (YAGNI)
  • Supervisor / progress-critic outer loop (a hook point may remain, but none built)
  • Plan-execute / replan; subagents; multi-agent orchestration
  • Capture-time semantic skip of trivial exchanges
  • Multi-writer concurrency on one KB
  • Cross-call resumable long-running tasks (host re-feeds history)
  • Runnable code/ projects

§ Resolved decisions

The three items left open at review are now settled — the spec is ready for implementation planning.

1 ✓

Integration mechanism

Library import. The agent imports kb-wiki Layer 1 functions directly — type-safe, no per-op subprocess spawn. Lightest at runtime.

2 ✓

Package name

kb-wiki-agent. Developed as a workspace package inside this repo (it also edits scripts/ for the archivedPending extension).

3 ✓

Multi-instance concurrency

Deferred — acceptable. Single-writer is fine for now; advisory locking is a later add only if a multi-instance deployment needs it.
