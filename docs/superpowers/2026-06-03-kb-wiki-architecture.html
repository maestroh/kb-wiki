kb-wiki — Portable Agent Memory

A git-backed memory loop for agents, packaged as a Claude Code plugin. An agent captures findings as it works, consolidates them into an interlinked wiki, recalls them later without going stale, and syncs the whole thing to git — so the same memory is usable on another machine and by another runtime. The redesign puts all judgment in a thin skill layer over deterministic, individually-testable TypeScript scripts that own every on-disk invariant. Synthesized from the 2026-06-01 design spec and the four 2026-06-02 implementation plans.

1The agent memory loop

This is what the system is for. An agent (headless, or interactive Claude) cycles through four phases against a git-backed store. Core memory — small, durable facts about the user — stays resident through every turn. Two boundary guards keep recent context from being lost before it's persisted.

1.1 — Memory tiers (and their database analogues)

The design is explicitly an LSM-tree / memtable store: a compacted long-term layer plus an un-flushed delta, queried together so reads are never stale. The _index.md tiering — front-matter summaries that page in full articles on demand — is what the spec calls "the core value."

TierOn diskLoadedMemory-system analogue
Core memorycore/_index.mdAlwaysMemGPT core / resident working set — durable cross-project facts
Working-set indexroot + project _index.md frontmatterAlways (summaries)Page table / catalog — pointers + one-line summaries
Consolidated articleswiki/<slug>.mdOn demandCompacted long-term store — paged in when relevant
Pending rawraw/ + ## Raw Sources (pending)Merged on readMemtable / write buffer — recent, not yet compacted
Archiveraw/_archive/RarelyCold storage — superseded originals
Why read-merge matters. Because consolidation (compile) is deferred, the wiki alone is stale. Recall always reads wiki ∪ pending-raw — compacted depth plus the un-flushed delta — so a finding captured seconds ago is recalled immediately. This closes Gap 1 (ingested-but-not-compiled). The PreCompact guard closes Gap 2 (in-conversation-but-not-ingested) by writing the about-to-be-lost context into raw/ before the agent's context window is summarized away.

1.2 — Two runtimes, one memory

Portability is the thesis: the deterministic script layer exists so that different reasoners share one git-backed memory without drifting. Any writer that upholds the on-disk contract can participate.

Interactive Claude Code reasoner present

  • Enters through the skill layer → calls Layer-1 scripts.
  • Synthesizes during compile for free (no API key) at session boundaries or on explicit /kb-compile.
  • This plugin.

Headless agent backend out of scope here

  • Calls Layer-1 scripts directly with its own orchestration (MemoryLoop timing, MemoryWriter selection).
  • Synthesizes via its own provider key (OpenAI).
  • We don't modify it — we only guarantee a contract-compliant repo it can consume.
The shared contract is the product. A fresh git clone is fully functional — no state lives outside the repo. Chat with an agent on one machine, store findings, pull on another, and use the memory to drive building an app or writing a post. The invariants in §8 are what make that hand-off safe across runtimes.

2The core principles

Three ideas drive every design decision below. If you remember only these, the rest follows.

① raw is the source of truth

  • raw/ originals are never edited — only archived.
  • The wiki/ is derived from raw via compilation.
  • Deferring (or skipping) compilation never loses information.

② Synthesis is caller-side

  • The in-loop reasoner (the LLM) does all judgment: what to write, how to link, which concept is which.
  • Scripts are pure: argv/stdin → JSON on stdout, no LLM, no prompts.
  • The boundary is explicit — a brief goes out, a commit comes back.

③ The registry is authoritative

  • Root _index.md frontmatter (projects:) is the single source of truth for which projects exist and their article counts.
  • Skills read the registry — they never scan the filesystem to discover structure.

④ Capture now, compile later

  • Ingest only stages raw and records it as pending; it does not compile.
  • Queries read-merge wiki ∪ pending-raw, so answers are fresh even before compilation runs.
  • Compilation happens explicitly (/kb-compile) or automatically at session boundaries.

4On-disk layout

The knowledge base is a self-contained git repo at $KNOWLEDGE_BASE. One directory per project; raw/ and wiki/ sit side by side so derivation is local and obvious.

$KNOWLEDGE_BASE/
├── _index.md              # root registry — frontmatter `projects:` is authoritative
├── core/_index.md         # always-loaded durable facts about the user (kind: kb-core)
├── projects/
│   └── <name>/            # kebab-case, canonical project name
│       ├── raw/           # SOURCE OF TRUTH — never edited
│       │   ├── notes/  documents/  videos/  links/  images/  _archive/
│       ├── planning/      # plans, specs, todos
│       ├── assets/        # datasets, designs, large artifacts
│       └── wiki/          # DERIVED — synthesized articles
│           ├── _index.md  # kind: kb-project + Articles / Raw Sources (pending|compiled|archived)
│           └── <article>.md
├── .obsidian/             # vault config (useMarkdownLinks: false)
└── .kb-active             # gitignored — active project pointer for hooks
The project wiki/_index.md body has a fixed shape. Three stable markdown sections — ## Articles, ## Raw Sources (pending), ## Raw Sources (compiled) (plus archived) — are parsed and rewritten mechanically by index-sections.ts. This is how a source moves pending → compiled without an LLM in the loop.

5Layer-1 module map & dependencies

Three contract modules at the base; eight task scripts above, each a thin CLI that imports the contract and never re-implements frontmatter, section, or registry logic. compile-commit.ts is the keystone — it is the only script that touches articles, the project index, and the root registry in one transaction.

6The four data flows

Everything the system does is one of these. Notice where the LLM reasoner enters and exits — that boundary is the whole design.

5.1 — Ingest (capture, no compile)

5.2 — Compile (the brief → synthesize → commit boundary)

5.3 — Ask (read-merge keeps answers fresh)

5.4 — Sync (and where it fires automatically)

sync.ts ordering det

  1. git add -A — stage everything.
  2. Commit if dirty — must happen before pull, or rebase aborts on a dirty tree.
  3. git pull --rebase onto the remote.
  4. git push — token-injected URL when KNOWLEDGE_GIT_TOKEN is set (headless auth, never persisted).

When it runs automatically

  • SessionEnd hook → sync.ts. Flush the KB when a session closes.
  • PreCompact hook → hook-precompact.ts (capture recent transcript into the active project's raw/) → then sync.ts.
  • Hooks read .kb-active to know which project to act on, and never fail the session — every step is best-effort.
  • /kb-sync delegates to the same script, falling back to its conflict-resolution prose only on a rebase conflict.

8Invariants the design holds

State integrity

  • Project names are canonical, kebab-case, validated at both creation and commit.
  • The root registry is authoritative for which projects exist; article counts stay in sync on every commit.
  • Every pending source is recorded on disk (in the index) — capture is durable even if compile never runs.

Safety

  • compile-commit validates first and writes nothing on failure — no partial articles.
  • migrate refuses to run if projects/ already exists — no clobbering.
  • Hooks are best-effort and never fail a session.

Freshness

  • Queries always read-merge wiki ∪ pending-raw, so recency is never lost to deferred compile.
  • Articles are synthesized, not copied; every article lists its contributing sources.

Separation of concerns

  • SKILL.md files hold orchestration + judgment only; all mechanical I/O lives in scripts.
  • Scripts are pure (argv/stdin → JSON), unit-testable, and LLM-free.
  • Same-project links are [[article]]; cross-project links are [[projects/<other>/wiki/<article>]].
